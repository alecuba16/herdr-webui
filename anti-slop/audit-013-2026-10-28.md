## Findings

Three real defects found during live e2e validation, all fixed:

1. Slider drag killed the row mid-drag. The first version of the row
   used a direct setter on oninput, which routed every drag tick through
   the full refresh/render (screen.innerHTML swap) and destroyed the
   slider being dragged. Fixed: oninput goes through the debounced
   commit (setSettingDebounced) and onchange through the immediate commit
   (commitSettingFromChange), with scrollLines registered in
   settingCommitPaths. The e2e now proves a driven slider persists 7
   and the row node survives the commit without a DOM swap.
2. Wheel math was not at parity. The desktop accumulator carries
   sub-row pixel deltas across events (terminalWheelDeltaPixels) and
   treats deltaMode 1 as exact ±stepLines, deltaMode 2 as a page
   (term.rows). The first mobile version rounded each event
   independently (trackpads stall one row short) and read a page from
   state.termRows, which mobile never sets. Fixed: accumulator state,
   deltaMode 1 = ±stepLines, deltaMode 2 = ±(term.rows || 24).
3. Double wheel scroll: the adapter keeps its own fallback wheel
   listener (added at create, bubble phase) and scrolls one extra row on
   every step. Desktop wins this via capture registration plus
   stopImmediatePropagation (handleTerminalWheel); the mobile handler had
   neither. Fixed: mobile handleWheel registers capture: true and calls
   stopImmediatePropagation after scrolling (desktop parity), killing the
   adapter's extra row. Live e2e proves an exact 7-row step at speed 7
   (delta 119 = 7 x 17px rows, no eighth row).

Probe defects found and fixed (test code, not shipped code):

- ss4 asserted undefined === undefined when its probe errored; now it
  requires the mint and a defined delta.
- The recents Open click landed on nothing: the recents rows live inside
  a closed disclosure. The probe now expands it first, mirroring the
  decouple runner.
- The wheel probe measured from the scrollback bottom, where a downward
  step clamps to zero. It now resets to the top first.

## Notes

- The desktop Scroll speed row pre-exists (optScrollLines in
  core.js settings HTML + bindings.js commit path); this change only
  adds the mobile counterpart, no desktop UI touched.
- Touch pan scroll is intentionally unaffected: finger-follow is native
  and the setting contract is lines-per-wheel-step on both layouts.
- The wheel handler's yield conditions (SGR mouse tracking, alt screen)
  run before any scroll: a program that owns the wheel still gets it.
